# 📘 Методичка по использованию логирования в проекте

## 1. Зачем нужно логирование
Логирование помогает отслеживать работу приложения:
- кто вызвал эндпоинт,
- какие действия выполнялись,
- где возникла ошибка,
- как развивались события.

Это важно для отладки, анализа инцидентов и сбора статистики.

---

## 2. Структура логирования в проекте
Мы используем централизованный логер app_logger. Логи пишутся и в файл, и в консоль.

### Формат записи:
2025-09-22 14:25:10 | INFO | ivan | 42 | Вызов эндпоинта: get_user

- 2025-09-22 14:25:10 — время события  
- INFO — уровень логирования  
- ivan — имя пользователя  
- 42 — ID пользователя  
- Вызов эндпоинта: get_user — сообщение  

---

## 3. Где хранятся логи
- Основной лог-файл задаётся в LOG_FILE.
- Используется ротация логов (RotatingFileHandler):
  - максимальный размер = MAX_BYTES,
  - количество резервных копий = BACKUP_COUNT.

---

## 4. Как писать логи вручную
Для этого есть функция log_event.

from src.logger import log_event

log_event("info", "Пользователь создал заказ", username="ivan", user_id=42)
log_event("warning", "Попытка доступа без авторизации")
log_event("error", "Ошибка при сохранении заказа", username="alex", user_id=13)

Параметры:
- level — уровень (info, warning, error, debug и др.)
- message — текст сообщения
- username — имя пользователя (по умолчанию SYSTEM_USERNAME)
- user_id — ID пользователя (по умолчанию ZERO_DEFAULT_USER_ID)

---

## 5. Как логировать вызовы эндпоинтов (FastAPI)
Есть декоратор @log_endpoint, который пишет лог при вызове.

from fastapi import APIRouter, Depends
from src.logger import log_endpoint

router = APIRouter()

@router.get("/users/me")
@log_endpoint("info")
async def get_user(user=Depends(get_current_user)):
    return {"id": user.id, "username": user.username}

В лог попадёт:
2025-09-22 14:30:05 | INFO | ivan | 42 | Вызов эндпоинта: get_user

---

## 6. Уровни логирования
- DEBUG — отладка
- INFO — обычные события
- WARNING — что-то пошло не так, но не критично
- ERROR — ошибка, действие не выполнено
- CRITICAL — критическая ошибка, сервис может упасть

---

## 7. Лучшие практики
✅ Логируй ключевые события (авторизация, ошибки, важные действия).  
✅ Добавляй контекст (имя и ID пользователя, параметры).  
❌ Не логируй пароли и токены.  
❌ Не используй много DEBUG в продакшене.

## 8. Логирование и мониторинг

В проекте настроено централизованное логирование через модуль `logging` и обработчик RotatingFileHandler.

### Реализовано:
- Логирование ведётся в файл (ограничение по размеру и количество ротаций задаются константами) и на консоль.
- В каждом сообщении указываются:
  - дата и время события,
  - уровень события (INFO, ERROR, WARNING и др.),
  - имя пользователя (username) и его идентификатор (id),
  - описание события.
- Если пользователь не передан — в лог записываются SYSTEM и 0 (значения SYSTEM_USERNAME и ZERO_DEFAULT_USER_ID).

Пример записи:
2025-09-22 14:25:10 | INFO | SYSTEM | 0 | Ошибка при сохранении заказа

### Использование:
- Для ручного логирования используется функция log_event(level, message, username, user_id).
- Для эндпоинтов FastAPI используется декоратор @log_endpoint, который автоматически пишет лог при вызове.

### Мониторинг:
- Задачи Celery отслеживаются через Flower.
- Логирование совместимо с асинхронной архитектурой проекта.

### Ключевые моменты архитектуры:
- Проект асинхронный.
- Развёртывание осуществляется через контейнеризацию (Docker).
- Опционально: настроить Redis для кеширования меню и акций, чтобы ускорить ответы.
- Для всех данных должна быть настроена валидация.
- Ограничения по бизнес-логике:
  - бронирования пользователя не должны пересекаться,
  - нельзя бронировать даты в прошлом,
  - нельзя изменять прошедшие и активные бронирования.
